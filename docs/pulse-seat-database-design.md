# Pulse Seat Database Design

> Status: Draft for review  
> Source: `docs/pulse-seat-system-design.md`, `docs/pulse-seat-technical-report.md`  
> Target stack: PostgreSQL managed by Neon, Redis, Elasticsearch, MinIO/S3-compatible storage

## 1. Mục tiêu thiết kế

Tài liệu này thiết kế database cho Pulse Seat theo hướng microservices. Mỗi service sở hữu schema riêng, tự quản lý migration và không truy vấn trực tiếp bảng của service khác. Các service giao tiếp qua REST/gRPC cho command/query đồng bộ và Kafka/outbox cho đồng bộ dữ liệu bất đồng bộ.

Mục tiêu chính:

- Giữ giao dịch đặt vé an toàn khi nhiều người cùng giữ chỗ.
- Tách rõ ownership dữ liệu giữa Booking, Payment, Ticket, Identity và Notification.
- Dễ scale các bảng có tải cao như seat availability, reservation, payment webhook, notification log, outbox.
- Phù hợp triển khai MVP trên Neon managed PostgreSQL, có thể tách database/cluster khi traffic tăng.

## 2. Quy ước chung

### 2.1 Schema ownership

| Schema | Service sở hữu | Vai trò |
| --- | --- | --- |
| `identity` | Identity Service | User, session, role, organizer owner |
| `booking` | Booking Service | Event catalog, venue, seat map, reservation, booking |
| `payment` | Payment Service | Payment transaction, refund, webhook |
| `ticket` | Ticket Service | Ticket issuance, QR token hash, check-in scan |
| `notification` | Notification Service | Template, delivery job, delivery log |
| `search_read` | Search/Projection worker | Read model phục vụ search/filter, có thể chuyển sang Elasticsearch |
| `ops` | Platform/Ops | Audit, processed event, DLQ metadata nếu cần dùng chung |

Trong MVP có thể đặt các schema này trong cùng một Neon database để giảm vận hành. Mỗi service vẫn dùng user/role riêng và chỉ có quyền trên schema của mình. Khi scale, có thể tách dần thành database hoặc Neon project riêng theo service.

### 2.2 Kiểu dữ liệu chuẩn

| Loại dữ liệu | Quy ước |
| --- | --- |
| Internal ID | `BIGINT GENERATED BY DEFAULT AS IDENTITY` |
| Public ID | `external_id VARCHAR(64) UNIQUE`, dùng ULID/UUID hoặc prefix như `evt_`, `bk_`, `tkt_` |
| Tiền | `BIGINT` theo minor unit, ví dụ VND là đồng, USD là cent |
| Tiền tệ | `CHAR(3)` theo ISO-4217 |
| Thời gian | `TIMESTAMPTZ`, không dùng `TIMESTAMP` không timezone |
| Trạng thái | `VARCHAR(32)` kèm `CHECK`, ưu tiên linh hoạt hơn enum trong giai đoạn đầu |
| Metadata | `JSONB`, chỉ dùng cho dữ liệu phụ trợ, không thay thế cột truy vấn chính |
| PII | Email, phone, name cần được che log; cân nhắc mã hóa cấp ứng dụng cho dữ liệu nhạy cảm |

### 2.3 Cột audit mặc định

### 2.4 Idempotency

Các command ghi dữ liệu cần hỗ trợ idempotency, đặc biệt:

- Reserve seats
- Create booking
- Create payment
- Confirm payment webhook
- Issue tickets
- Send notification

Mẫu bảng dùng trong từng schema cần idempotency:

| Table | Column | Type | Ghi chú |
| --- | --- | --- | --- |
| `{schema}.idempotency_keys` | `id` | `BIGINT PK` | Internal ID |
|  | `scope` | `VARCHAR(64)` | Ví dụ `reserve_seats`, `create_payment` |
|  | `idempotency_key` | `VARCHAR(128)` | Key từ client/service |
|  | `request_hash` | `VARCHAR(128)` | Hash body để phát hiện replay khác payload |
|  | `response_status` | `INTEGER` | HTTP/gRPC mapped status |
|  | `response_body` | `JSONB` | Response đã lưu |
|  | `resource_type` | `VARCHAR(64)` | Ví dụ `reservation`, `payment` |
|  | `resource_id` | `BIGINT` | ID tài nguyên đã tạo |
|  | `expires_at` | `TIMESTAMPTZ` | TTL logic |
|  | `created_at`, `updated_at` | `TIMESTAMPTZ` | Audit |

Index bắt buộc:

- `UNIQUE (scope, idempotency_key)`
- `INDEX (expires_at)`

Đây là bảng critical path cho giữ ghế reserved seating.

| Column | Type | Constraint/Ghi chú |
| --- | --- | --- |
| `performance_id` | `BIGINT` | FK `booking.performances(id)` |
| `seat_key` | `VARCHAR(128)` | ID ghế trong `seat_maps.layout_json`, ví dụ `A-12` |
| `tier_id` | `BIGINT` | FK `booking.ticket_tiers(id)` |
| `section_label` | `VARCHAR(64)` | Snapshot section |
| `row_label` | `VARCHAR(32)` | Snapshot row |
| `seat_number` | `VARCHAR(32)` | Snapshot seat number |
| `seat_label` | `VARCHAR(64)` | Label hiển thị |
| `status` | `VARCHAR(32)` | `AVAILABLE`, `HELD`, `SOLD`, `BLOCKED`, `VOID` |
| `reservation_id` | `BIGINT` | Nullable FK `booking.reservations(id)` |
| `booking_id` | `BIGINT` | Nullable FK `booking.bookings(id)` |
| `held_until` | `TIMESTAMPTZ` | Nullable |
| `version` | `BIGINT` | Optimistic locking |
| `updated_at` | `TIMESTAMPTZ` | Audit |

Constraints/indexes:

- `PRIMARY KEY (performance_id, seat_key)`
- `CHECK (status <> 'HELD' OR (reservation_id IS NOT NULL AND held_until IS NOT NULL))`
- `CHECK (status <> 'SOLD' OR booking_id IS NOT NULL)`
- `INDEX (performance_id, tier_id, status)`
- `INDEX (performance_id, section_label, status)`
- `INDEX (status, held_until) WHERE status = 'HELD'`
- `INDEX (reservation_id) WHERE reservation_id IS NOT NULL`
- `INDEX (booking_id) WHERE booking_id IS NOT NULL`

Giao dịch giữ ghế nên lock theo danh sách ghế:

```sql
SELECT *
FROM booking.seat_availability
WHERE performance_id = $1
  AND seat_key = ANY($2)
FOR UPDATE;
```

Sau đó chỉ update các ghế đang `AVAILABLE` hoặc `HELD` đã hết hạn.

## 10. Luồng giao dịch quan trọng

### 10.1 Reserve reserved seats

1. Client gọi Booking API với `performance_id`, danh sách `seat_key`, `tier_id`, `idempotency_key`.
2. Booking mở transaction.
3. Lock các dòng `booking.seat_availability` bằng `FOR UPDATE`.
4. Kiểm tra ghế `AVAILABLE` hoặc `HELD` đã hết hạn.
5. Tạo `booking.reservations` và `booking.reservation_items`.
6. Update `seat_availability` sang `HELD`, set `reservation_id`, `held_until`, tăng `version`.
7. Ghi `domain_events` + `outbox_messages` trong cùng transaction.
8. Commit.

Isolation khuyến nghị: `READ COMMITTED` với row-level lock là đủ cho reserved seats.

### 10.2 Create payment qua gRPC

1. Booking tạo booking trạng thái `PENDING_PAYMENT`.
2. Booking gọi `PaymentService.CreatePayment` qua gRPC.
3. Payment kiểm tra idempotency key.
4. Payment tạo `payment.payments` và gọi provider nếu cần.
5. Payment trả `payment_external_id`, `status`, `client_action`.
6. Booking lưu `payment_external_id` và chuyển booking sang `PAYMENT_PENDING`.

Booking không ghi trực tiếp bảng Payment. Payment không update trực tiếp bảng Booking.

### 10.3 Confirm payment webhook

1. Provider gọi Payment webhook.
2. Payment ghi `payment.payment_webhooks`, dedupe bằng `(provider, provider_event_id)`.
3. Payment update `payment.payments`.
4. Payment phát event `PaymentCaptured`.
5. Booking consumer nhận event và confirm booking/reservation.
6. Booking phát event `BookingConfirmed`.
7. Ticket Service nhận event và issue tickets.
8. Notification Service gửi email/SMS.

### 10.4 Check-in ticket

1. Staff scan QR.
2. Ticket Service hash token và lookup `ticket.tickets.qr_token_hash`.
3. Lock ticket row bằng `FOR UPDATE`.
4. Nếu `ACTIVE`, update sang `USED`, set `used_at`.
5. Nếu đã `USED`, trả kết quả duplicate từ trạng thái hiện tại; MVP không lưu scan history riêng.

## 12. Neon PostgreSQL deployment notes

### 12.1 MVP deployment

Khuyến nghị MVP:

- Một Neon project cho môi trường `dev/staging/prod`.
- Một database `pulse_seat`.
- Mỗi service một schema và một DB role riêng:
  - `pulse_identity_app`
  - `pulse_booking_app`
  - `pulse_payment_app`
  - `pulse_ticket_app`
  - `pulse_notification_app`
- Migration dùng direct connection.
- Runtime app dùng pooled connection.

### 12.2 Connection pooling

Quy ước:

- API service dùng pooled DSN cho request runtime.
- Migration/DDL dùng direct DSN.
- Không phụ thuộc session-level state trong pooled mode.
- Advisory lock hoặc transaction lock chỉ dùng trong transaction rõ ràng.

### 12.3 Backup và branch

Neon branch có thể dùng cho preview environment và test migration. Production cần cấu hình backup/PITR theo plan Neon đang dùng. Trước migration lớn như partitioning hoặc đổi status contract, tạo branch staging để chạy rehearsal.

## 13. Migration plan đề xuất

### Phase 1: Foundation

- Tạo schema `identity`, `booking`, `payment`, `ticket`, `notification`, `ops`.
- Tạo role/service user theo schema.
- Tạo bảng common: `idempotency_keys`, `domain_events`, `outbox_messages`.
- Tạo Identity tables: `users`, `roles`, `organizers`.

### Phase 2: Booking core

- Tạo catalog: `artists`, `venues`, `events`, `media_assets`.
- Tạo seat map: `performances`, `seat_maps`, `ticket_tiers`.
- Tạo inventory: `seat_availability`.

### Phase 3: Checkout

- Tạo `reservations`, `reservation_items`, `bookings`, `booking_items`.
- Tạo Payment tables: `payments`, `payment_webhooks`, `refunds`.
- Tạo transaction tests cho reserve/confirm/expire hold.

### Phase 4: Ticketing and notification

- Tạo `ticket.tickets`.
- Tạo `notification.notification_templates`, `notification.notification_jobs`, `notification.notification_logs`.
- Tạo outbox consumers và processed event dedupe.

### Phase 5: Read model and scale

- Tạo `search_read.event_cards` cho MVP search.
- Đồng bộ sang Elasticsearch/OpenSearch khi search phức tạp hơn.
- Thêm partition cho notification log, webhook, domain event và outbox khi dữ liệu tăng.

## 14. Câu hỏi cần chốt trước khi implement migration

- Public ID format dùng ULID có prefix hay UUID v7?
- MVP dùng một Neon database nhiều schema hay tách database theo service ngay từ đầu?
- Có yêu cầu mã hóa PII cấp cột cho buyer/attendee không?
- Provider payment đầu tiên là Stripe, VNPay, MoMo hay mock provider?
- Seat map layout sẽ import từ tool nào và `layout_json` cần contract cụ thể ra sao?
- Retention cho webhook payload, notification log và outbox/domain event là bao lâu?
